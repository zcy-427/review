# 第一章 绪论

## 1.1 研究背景与意义

中医方药推荐需要综合患者的症状表现、证候判断、治法以及方剂和药味之间的关系。相关研究通常将这一过程表示为“症状—证候—治法—方剂—药味”的多层映射，并将中药处方推荐建模为多输出或多标签预测问题[1]。与普通文本检索相比，该任务不仅要求系统找到语义相关的方剂，还需要处理中医术语异名、症状表述差异、方剂组成关系以及推荐依据追溯等问题。因此，如何把分散在方剂条目、中药属性和方药关系中的知识组织起来，并依据用户输入形成可解释的候选结果，是中医药信息化研究中的一个具体问题。

近年来，机器学习、知识图谱和大语言模型为中药处方推荐提供了新的技术路径。传统机器学习和深度学习方法可以从症状与处方数据中学习映射关系；知识图谱能够以实体和关系的形式组织症状、证候、治法、方剂及药味；大语言模型则具有较强的自然语言理解和生成能力，可用于病历信息抽取、术语归一、检索结果整合和说明文本生成[1,4,6]。与此同时，检索增强生成（Retrieval-Augmented Generation，RAG）通过在生成前检索外部知识，使模型回答能够与特定知识库建立联系，已经被用于中医证候推断、处方推荐、中成药推荐和中医知识问答等任务[2-3,7-8]。

然而，直接利用大语言模型生成处方仍存在明显局限。已有研究报告了诊断分析错误、无依据药味、模型间结果波动以及跨病种泛化不足等问题[4,6-8]。模型生成的解释虽然语言流畅，但不必然忠实反映推荐结果的真实计算过程，更不能据此推导医学因果关系。另一方面，真实中医病历和处方数据通常涉及隐私、授权与质量控制，公开可复现的数据较为有限[1,6,8]。这些问题说明，中药方药推荐系统不能只依赖大模型的参数知识，而应将可追溯的数据、结构化关系、受限候选空间和明确的实验边界结合起来。

基于上述背景，本文拟设计并实现一个基于知识图谱与检索增强的中药方药推荐系统。系统面向用户输入的症状描述或模拟中医病历，通过输入校验、术语标准化、关键词检索、向量检索和知识图谱关系分析，返回候选基础方、药味集合及其匹配依据。核心推荐链路不依赖外部大语言模型，默认使用规则、词典和确定性模板完成输入解析与结果说明；大语言模型仅作为可选适配层，用于整理已经检索到的结构化证据，且不得生成数据库之外的方剂、药味、剂量或来源。该研究的意义主要体现在以下两个方面。

第一，在方法层面，本文尝试把混合检索、知识图谱、受限候选和确定性证据说明组织为一条可评价的处理链，并分别考察关键词检索、向量检索及图关系重排序的作用。系统将推荐结果与原始方剂条目、方药组成和图路径关联，使“为什么输出该候选”能够落到具体数据关系，而不是依赖大模型自行生成的推理文字。

第二，在工程层面，本文以课程研究原型为目标，采用 Java 25 LTS 与 Spring Boot 4.1.x 构建单体后端，以 Apache Lucene 实现 BM25 检索，以 PostgreSQL/pgvector 保存规范化实体、原始来源、检索文本、向量和实验记录，并将 Neo4j 作为从 PostgreSQL 单向、幂等构建的知识图谱投影。前端采用 Vue 3、TypeScript、Vite 和 Element Plus，数据库服务由 Docker Compose 统一编排。该设计有助于形成从 Excel 数据导入、知识组织、候选检索到证据输出的完整系统闭环，并为后续更换为合规病历数据保留扩展空间。

需要说明的是，本文不研究真实患者的临床处方生成，也不评价治疗效果。系统输出仅作为课程项目中的方药知识检索和推荐演示，不提供个体化剂量，不用于实际医疗决策。

## 1.2 相关研究现状

### 1.2.1 数据驱动的中药处方推荐

中药处方推荐已经形成多种计算范式。Dong 等将现有方法概括为传统机器学习、主题模型、深度学习与图结构方法、序列生成方法以及大语言模型方法五类[1]。理想情况下，处方推荐应综合人口学信息、疾病状态、病史、症状和检查指标，但由于数据可得性、标准化和隐私限制，多数研究仍将患者表示简化为症状集合，并预测相应证候、治法或药味集合[1]。这种症状级建模降低了数据要求，但也会遗漏舌脉、病程、合并用药和个体差异等重要信息。

针对药味推荐，Zhuang 等将中医知识图谱信息注入语言模型，并把处方生成转化为固定药味空间中的多标签预测，以限制模型输出范围[4]。该方法说明，受限词表可以减少词表外药味，但仍不能自动保证配伍、剂量和临床解释的正确性。Wang 等进一步采用知识蒸馏、LoRA 和直接偏好优化，构建“症状分析—处方推荐—处方解释”的输出流程[6]。其研究直接证明了可解释处方推荐可以作为计算任务进行训练和评价，同时也报告了分析错误、幻觉和偏好模型与临床相关性不完全一致等限制。

总体而言，数据驱动方法能够学习症状与方药之间的统计关系，但其效果依赖训练数据覆盖范围、标签质量和药味分布。真实处方数据往往来自单一机构、单一医家或特定病种，低频药味和分布外输入仍是主要困难[1,4,6]。因此，课程项目若缺少真实病历数据，应明确将实验定义为代理任务，不能将方剂主治文本上的效果直接解释为患者级个性化处方能力。

### 1.2.2 中医药知识图谱研究

知识图谱能够通过节点、属性和关系表达中医药领域中的多层知识。谭平等使用 BIO 标注、BiLSTM-CRF 和人工规则完成脾胃病实体抽取，并通过 Neo4j 存储中医诊断、临床表现、证候、治则、方剂及中药等关系，构建了包含 2 849 个实体和 10 类关系的领域知识图谱[9]。该研究验证了 Neo4j 在中医知识组织、查询和可视化方面的可实施性，但其评价对象主要是命名实体识别和图谱构建，而不是方剂推荐性能。

在知识图谱与大模型结合方面，Zhuang 等利用症状、舌象和脉象相关知识辅助药味预测[4]；Zhang 等在预印本研究中使用 Neo4j、社区发现和 GraphRAG 组织方剂知识，并结合模型微调进行处方相关任务[5]；Zhong 等则构建了超过 20 万实体的中医知识图谱，用于知识检索、问答和可视化，并将通用知识模块与医家经验处方模块分开训练和评价[8]。这些工作表明，中医知识图谱适合表达症状、证候、治法、方剂和药味之间的关系，也可以为检索和生成模型提供结构化上下文。

现有研究仍存在两点不足。其一，完成图谱构建并不等于已经证明图谱能够提高推荐准确率，图关系对推荐结果的增益需要通过与非图方法的对照或消融实验验证。其二，知识图谱质量高度依赖实体标准化、关系抽取和来源校验。若药名异名、炮制品或同方异名未得到统一，图中的节点和边可能进一步放大原始数据误差。

### 1.2.3 检索增强生成与大语言模型研究

RAG 的基本思路是在大语言模型生成结果前，从外部知识库中召回相关证据。Huang 等基于 6 747 例睡眠障碍门诊记录构建处方和证候知识库，研究了文本分块、中文向量表示和 RAG 在特定病种中的应用[2]。Qin 等整理 8 644 份中成药说明书，通过术语标准化、语义检索和 Top-3 证据增强实现中成药推荐[3]。这两项研究分别说明了 RAG 在中医门诊知识和中成药说明书场景中的可行性，但其数据类型和输出目标与个性化汤剂药味推荐并不完全相同。

Fan 等提出面向中医风湿病的 CoT-RAG 框架，将专家病例、经典文献和指南作为检索来源，并通过重排序和分阶段推理完成症状、诊断及方剂相关任务[7]。Zhong 等采用 Faiss、RAG、知识图谱和两个功能分离的大模型，分别支持中医知识问答和特定医家的处方参考[8]。这些研究表明，检索增强、结构化推理和模块化服务能够用于中医知识与处方相关系统，也提示通用知识和医家经验并不一定适合简单混合：Zhong 等的实验中，继续加入通用知识后，模型与特定医家处方模式的一致性反而降低[8]。

尽管如此，现有文献尚未直接验证本文拟采用的“BM25 + 向量检索 + 倒数排名融合（Reciprocal Rank Fusion，RRF）+ Neo4j 图关系重排序”组合。不同研究所使用的数据、模型、检索器和评价方法差异较大，不能直接推出某一种组合在本文数据上必然有效。因此，本文将混合检索和图关系重排序作为待验证的方法设计，通过统一数据划分和评价指标进行比较，而不预设其一定优于单一检索。

### 1.2.4 现有研究的主要不足

综合现有文献，与本文任务直接相关的问题主要包括以下几个方面。

（1）**数据可复现性与任务适配不足。** 多项研究使用不公开的患者数据或特定医家病例，公开材料难以直接复现。现有方剂知识数据可以支撑方药检索，但不能等同于包含完整四诊信息的真实病历。

（2）**自然语言与标准术语之间存在差异。** 用户输入可能包含口语表达、否定症状、持续时间和同义词，而方剂及中药数据通常使用规范化术语。错误的术语映射会影响后续检索和图查询。

（3）**检索与图推理的增益缺少统一验证。** 向量检索、知识图谱和重排序分别得到了一定支持，但其组合效果依赖具体数据，仍需设计可重复的对照实验。

（4）**生成解释不等于忠实解释。** 大语言模型可以生成症状分析和处方说明，但解释内容可能包含检索证据之外的知识，无法仅凭语言流畅度判断其是否真实反映推荐过程。

（5）**推荐边界与安全性仍需约束。** 现有研究尚不足以证明模型输出具有临床有效性和完整安全性。对于课程原型，应限制药味候选空间、保留来源、提示数据覆盖边界，并避免输出个体化剂量。

## 1.3 研究目标与问题定义

本文的总体目标是设计并实现一个面向症状描述和模拟中医病历文本的方药推荐原型。给定用户输入文本，系统首先进行长度、空值和模式校验，再通过词典、规则及可配置解析器抽取症状、否定信息、病程和可选证候等要素；随后在方剂知识库中完成关键词召回和语义召回，通过融合排序与知识图谱关系分析形成 Top-K 候选方剂；最后从规范化方药关系中获得药味集合，并使用确定性模板生成包含匹配证据、图路径、排名信息和来源记录的结果说明。

本文重点研究以下问题：

1. 如何对本地方剂、中药和方药关系数据进行规范化处理，构建可追溯的方药知识库与知识图谱？
2. BM25 与向量检索的融合能否在弱监督代理任务上提高方剂检索的 Recall@K、MRR 或 NDCG@K？
3. 加入症状、功效、方剂和药味之间的结构化关系后，图关系重排序能否在混合检索基础上带来额外增益？
4. 使用稳定候选 ID 和确定性证据模板，能否避免库外药味与无来源陈述，并在 Neo4j 不可用或图数据版本不一致时实现可解释降级？

本文使用本地 TCMIO 目录中的方剂表、中药表和方剂—药味关系表开展实验。其中，方剂表包含 1 493 条记录，方剂—药味关系表包含 13 403 条关系。由于该数据不包含真实患者的年龄、病程、舌脉、既往史、疗效和医生处方过程，本文将任务限定为“功效/主治或模拟症状文本到方剂与药味”的弱监督代理任务。数据的实际下载来源和再利用许可仍待进一步核验，因此当前仅用于本地课程研究，不公开分发原始数据。

## 1.4 主要研究内容

围绕上述目标，本文拟开展以下工作。

（1）**方药数据导入、清洗与规范化。** 原始 Excel 始终保持只读，使用 Apache POI 读取工作簿，通过 Spring Batch 分批导入和处理方剂、中药及方剂—药味关系。处理过程包括字段检查、重复关系清理、药名异名归一和方剂家族合并，并记录输入校验和、数据版本、规则版本、输入输出行数、未解析项和异常项，生成可复现实验 manifest。

（2）**方药知识库与知识图谱构建。** 以 PostgreSQL 作为唯一事实主库，使用 Flyway 管理数据库迁移，保存方剂、药味、功效、主治、原始来源、规范化映射、向量和 `dataset_version`；通过 pgvector 支持语义检索。根据主库数据单向、幂等地构建 Neo4j 图谱投影，表达症状/功效、证候、方剂和药味之间的可查询关系，并校验节点、边和数据版本。在线请求不跨库双写，数据修订只进入 PostgreSQL。

（3）**混合检索与候选排序。** 使用 Apache Lucene 实现 BM25 基线，使用 pgvector 实现向量检索基线，再通过 RRF 融合两路排名，并利用 Neo4j 图关系或 PostgreSQL 结构化字段进行候选重排序。召回深度、Top-K、RRF 参数和图谱权重均由配置管理。通过统一测试集比较各阶段的检索效果，判断混合方法和图关系是否具有实际增益。

（4）**受限方药推荐与证据说明。** 候选方剂和药味均从数据库稳定 ID 中选择。结果页展示标准化输入、命中的功效/主治文本、方剂组成、图关系路径、各阶段分数、数据版本和原始来源。默认解释由确定性模板生成；如启用 Spring AI 适配的外部模型，模型只能润色已经检索到的证据，输出必须经过方剂、药味、剂量和来源白名单校验，超时、失败或校验不通过时回退到模板结果。

（5）**系统设计与实现。** 后端采用 Java 25 LTS、Spring Boot 4.1.x、Spring Web MVC、Spring Data JPA、Spring Data Neo4j 和 Spring Boot Actuator，按 `dataset`、`formula`、`retrieval`、`graph` 和 `recommendation` 等业务能力组织单体应用；API 使用 Jakarta Bean Validation 校验输入，并通过 Spring `ProblemDetail` 返回稳定错误结构。前端采用 Vue 3、TypeScript、Vite、Element Plus 和 ECharts，实现症状/模拟病历输入、候选方剂切换、药味组成查看、图谱关系展示、错误/空结果/降级状态和醒目免责声明。PostgreSQL/pgvector 与 Neo4j 由 Docker Compose 组织本地环境。

（6）**实验、测试与评价。** 设置 BM25、Vector、Hybrid 和 Hybrid + KG 等对照条件，并增加 Neo4j 不可用或图数据版本不一致时的降级场景。方剂检索采用 Recall@K、MRR、NDCG@K 和 Top-K 命中率；药味集合采用 Precision、Recall、F1 和 Jaccard；证据说明考察引用支持率、证据链覆盖率、库外药味率和无来源陈述率。数据按基础方剂家族分组并使用固定随机种子，防止同方异名和近重复文本造成泄漏。后端使用 JUnit 5、Testcontainers 和 ArchUnit 验证业务规则、PostgreSQL/pgvector、Neo4j 同步、架构边界及降级行为；前端使用 Vitest、Vue Test Utils 和 Playwright 验证核心交互流程。

## 1.5 技术路线

本文的总体技术路线如下：

```text
本地方剂与中药数据
  → Apache POI 只读解析 + Spring Batch 分批处理
  → 数据清洗、药名归一、方剂家族合并与 manifest
  → Flyway 迁移 + PostgreSQL 事实主库
  → pgvector 向量索引 + Lucene BM25 索引
  → PostgreSQL 到 Neo4j 的单向幂等图投影
  → 用户症状/模拟病历输入
  → Bean Validation + 规则/词典解析与术语标准化
  → BM25 关键词召回 + 向量语义召回
  → RRF 融合排序
  → 图版本与可用性检查
  → 图关系重排序，或降级为 PostgreSQL 结构化重排序
  → 候选基础方与受限药味集合
  → 确定性模板生成来源、分数、图路径和不确定性说明
  → 可选 Spring AI 润色 + 白名单校验 + 模板回退
  → 对照实验、消融评价与端到端测试
```

在该路线中，PostgreSQL 中的规范化记录是唯一事实来源，Neo4j 只用于表达和查询关系，图数据可以由主库重复构建。在线请求只读两个数据库，不实施跨库双写。Neo4j 不可用或 `dataset_version` 不一致时，系统跳过图谱重排序并保留 BM25、向量检索和结构化证据输出。外部大语言模型默认关闭，也不参与候选方剂和药味的确定；启用时只能整理受限候选及其证据。由此形成的解释描述的是系统所使用的数据依据和排名过程，不被视为医学因果证明。

## 1.6 论文组织结构

本文暂按六章组织。

第一章为绪论，介绍研究背景与意义、相关研究现状、研究目标、主要内容和技术路线。

第二章介绍系统涉及的关键技术，包括 Java 与 Spring Boot、Apache Lucene BM25、向量检索、RRF、知识图谱、Neo4j、PostgreSQL/pgvector，以及可选大语言模型适配与确定性回退机制。

第三章介绍数据来源、数据质量问题、Apache POI/Spring Batch 导入流程、药名与方剂归一方法、版本 manifest、弱监督代理任务定义，以及方药知识库和知识图谱的构建过程。

第四章介绍系统需求、Spring Boot 单体架构、数据库设计、业务包划分、核心模块、接口和 Vue 前端交互流程，并说明跨数据库单向投影、故障降级与结果可追溯机制。

第五章介绍实验设计、固定数据划分、对照方法、评价指标、自动化测试及实验结果，重点分析混合检索、图关系重排序、确定性证据模板和故障降级的效果与失败案例。

第六章总结全文工作，说明研究限制，并讨论使用真实合规病历、扩展多病种数据和加强解释忠实性评价等后续方向。

## 1.7 本章小结

本章从中药方药推荐的数据特点出发，分析了数据驱动推荐、知识图谱、RAG 和大语言模型相关研究。现有文献能够支持症状到方药推荐、结构化知识组织和检索增强的总体方向，但仍存在数据难以复现、术语映射误差、生成幻觉、解释忠实性不足以及跨病种泛化有限等问题。针对这些问题，本文提出以本地方药数据为基础，使用 Spring Boot 构建单体应用，以 PostgreSQL/pgvector 作为唯一事实主库和向量检索层，以 Neo4j 作为可重建图投影，通过 Lucene BM25、向量检索、RRF 和图关系重排序形成候选结果，并优先使用确定性模板生成可追溯说明。外部大语言模型仅作为可选适配层，不属于基本推荐链路。上述方案的有效性将在后续章节中通过弱监督代理任务、对照实验、降级测试和端到端验证进行检验。
